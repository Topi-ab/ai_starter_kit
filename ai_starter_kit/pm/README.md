# Task and question kit

A starter kit for managing tasks, questions to the user and decisions in a repository worked on
by AI agents. Copy the contents of the kit directory into the root of a new project. The rules for agents are in `AGENTS.md` (`CLAUDE.md` imports it).

Requirements: Python 3.10+, standard library only. git is optional; `pm.py move` uses
`git mv` when the task is tracked.

## Start a new project

1. Copy the kit into the project root.
2. In `AGENTS.md`: fill in the section **Project**. Languages (English by default) are changed
   with `python3 pm/pm.py language set <key> <Language>`.
3. Optionally write what you already know into `PLAN.md`; the agent completes it in the scope stage.
4. Run `python3 pm/pm.py check` in a pre-commit hook or CI (it fails when the task store is invalid or an
   overview is stale).
5. Start the agent. The project begins in the workflow stage **Scope analysis**: the agent finds out
   the goal and the way there with you, creates the areas and topics and the meta tasks, and
   cannot start implementation until you approve the scope (`pm.py stage advance`).

## Command reference

The rules for using these are in `AGENTS.md`; this section is the reference it points to.

### Who changes which file

| File | Changed only by |

| `AGENTS.md` | the user, or an agent on request |
| `PLAN.md` | the agent, with the user's decisions (decision log) |
| `JOURNAL.md` | `pm.py journal` |
| `pm/<state>/T-NNNN/meta.json`, `task.md` | `pm.py new`, `edit`, `note`, `move`, `supersede` |
| `pm/questions/Q-NNNN.json` | `pm/question.py` |
| `pm/structure.json` | `pm.py group`, `phase` (new areas/topics with the user's consent) |
| `pm/counters.json` | the scripts |
| `pm/workflow.json` | `pm.py stage advance`, on the user's approval |
| `pm/background.json` → `pm/RUN_IN_BACKGROUND.md` | `pm/background.py set`, on the user's request |
| `pm/waiting.json` | `pm.py waiting` |
| `pm/spec/R-NNNN/` | `pm.py spec` / `ecr`; a draft's `text.md` by hand; a sealed one only by the user (`spec reseal`) |

### Tasks

```
python3 pm/pm.py new backlog|todo "Title" --description "what and why" --done-when "checkable criterion"
        [--request "<the user's words>"] [--group Area/Topic] [--phase P] [--depends T-1,T-2] [--context C]
        [--kind meta|work] [--implements R-1,R-2]
python3 pm/pm.py note T-NNNN "text" [--kind status|decision|result|not_done|correction|note]
python3 pm/pm.py edit T-NNNN [--title] [--group] [--phase] [--context] [--order N] [--depends IDS] [--needs X]
        [--clear-needs] [--implements IDS] [--kind]
python3 pm/pm.py move T-NNNN [T-NNNN ...] <state> [--reason TEXT] [--force]
python3 pm/pm.py supersede T-OLD --by T-NEW[,T-NEW2] --reason TEXT
python3 pm/pm.py list [ready|waiting|blocked|in-progress|done|dropped] [--group G] [--phase P]
python3 pm/pm.py json                          everything as JSON
python3 pm/pm.py stage [advance --approval "<the user's words>"]
python3 pm/pm.py waiting [add "text" [--task T-NNNN] | done W-NNNN]
python3 pm/pm.py journal "text"                JOURNAL.md entry, time stamp taken by the script
python3 pm/pm.py group list|add|rename|order|remove|describe ...
python3 pm/pm.py phase list|add|rename ...
python3 pm/pm.py language [set KEY LANGUAGE]
python3 pm/pm.py view [set|note|label|status|template|color|style ...]
python3 pm/pm.py                               regenerate the overviews
python3 pm/pm.py check                         validate; run before every commit
python3 pm/integrity.py [--json]               read-only: PASS, or FAIL with every problem
python3 pm/background.py [set foreground|threshold|background [--seconds N]]
```

`task.md` entries (labels from `pm/views.json` `note_labels`, in the task file language):

```
- **Created:** YYYY-MM-DD HH:MM                              new
- **Requested by the user:** "<their words>"                new --request
- **Description:** what and why.                            new --description
- **Done when:** a concrete, checkable criterion.           new --done-when
- **Started:** YYYY-MM-DD HH:MM                              move ... wip
- **Status YYYY-MM-DD HH:MM:** done so far, numbers, next    note "..."
- **Decision YYYY-MM-DD HH:MM:** user, Q-0012 a: "<their words>" (<translation>)    note --kind decision
- **Result YYYY-MM-DD HH:MM:** what came out; how verified   note --kind result
- **Not done YYYY-MM-DD HH:MM:** scope left out, T-ID       note --kind not_done
- **Done:** YYYY-MM-DD HH:MM                                 move ... done
```

`meta.json` fields: `group` ("Area" or "Area/Topic"), `phase` (a tag from `structure.json`),
`depends`, `questions` (added by `question.py ask --task`), `needs` (non-task prerequisites, shown
only), `context`, `order` (position within the topic; the priority), `kind` (`meta` or `work`),
`implements`, `superseded_by`.

### Requirements and change requests

```
python3 pm/pm.py spec [list] | spec show R-NNNN
python3 pm/pm.py spec new "Title" --text "statement" [--source "Q-0003 a / the user's words"] [--refines R-1,R-2]
python3 pm/pm.py spec link R-NNNN --refines R-1,R-2          parents of a draft
python3 pm/pm.py spec retitle R-NNNN "Title"                 title of a draft
python3 pm/pm.py spec suspect                                what to review after a change
python3 pm/pm.py spec review R-NNNN [R-NNNN ...] --approval "<the user's words>"   parents first
python3 pm/pm.py spec commit R-NNNN [R-NNNN ...] --approval "<the user's words>"
python3 pm/pm.py spec seal R-NNNN [R-NNNN ...] --approval "<the user's words>"     only on the user's request
python3 pm/pm.py spec reseal R-NNNN [--new-version] [--title "T"]   THE USER only, at a terminal, after a hand edit
python3 pm/pm.py ecr new "Title" --reason "why"
python3 pm/pm.py ecr change ECR-NNNN R-NNNN [--text "new text"] [--title "new title"]   (or edit the proposed file)
python3 pm/pm.py ecr retire ECR-NNNN R-NNNN
python3 pm/pm.py ecr add ECR-NNNN "Title" --text "new requirement" [--refines R-1]
python3 pm/pm.py ecr show ECR-NNNN                          diff, requirements to review, affected tasks
python3 pm/pm.py ecr approve|reject ECR-NNNN --approval "<the user's words>"
python3 pm/pm.py ecr apply ECR-NNNN                         keeps the old text as vK.md, raises the version
```

### Questions

```
python3 pm/question.py ask "Question text" [--task T-NNNN] --rec "recommended option" --opt "other option"
python3 pm/question.py answer Q-NNNN a [--note "..."]        a, b, ... or other / superseded / withdrawn [--force]
python3 pm/question.py show Q-NNNN                           repeat a question unchanged
python3 pm/question.py open | list [N]
```

## Why it is built this way

The kit merges the practices of several long-running agent sessions. Each choice below was
reached independently by more than one of them, or fixes a failure that one of them hit.

**Storage**
- *Everything the scripts read is JSON, changed only through the scripts.* Agents that parse or
  patch Markdown by hand sooner or later break it. The scripts validate every change, restore the
  old files when a change would make the store invalid, and refuse JSON that was edited by hand.
- *Generated Markdown is for the user only.* Each file starts with one agent note telling agents
  to use `list` / `json` instead; the rest contains only what the user needs.

**Workflow**
- *Scope analysis before implementation, enforced by the scripts.* In an early trial the
  agent implemented a whole engine from the first message without a plan or questions. The scope
  stage allows only meta tasks and no work; only the user's approval moves the project on.
- *Spec changes as a procedure plus `supersede`.* A trial showed a good impact analysis, but the
  agent rewired tasks before the user approved. Now: analysis, approval, then `supersede` (done
  tasks stay done, unfinished ones are dropped, dependents are listed).
- *Moving dependent tasks together.* `move` accepts several tasks and allows wip when the open
  dependencies are in progress, so `--force` is no longer the normal path; it prints what became
  ready, because an agent proposed the next task from an outdated listing.

- *task.md is written only through `note` (and `new`, `move`, `supersede`).* In one trial the agent
  repeatedly rewrote task.md by hand: deleted template lines, rewrote a finished task, adjusted
  time stamps. `new` now takes the description and criterion, so there is nothing to tidy.
- *Plain chat questions are recorded (`waiting`).* A new session started work while a
  "what next?" from the previous session was unanswered.
- *No unrequested features.* One agent added an input check nobody asked for.

- *Requirements with a lock, changed only through an ECR.* A trial showed a good spec-change
  procedure that rested on instructions only. Committed requirements are now locked by a hash of
  their text; the ECR records the user's approval, the proposed texts and the old versions, and
  computes the affected tasks from the tasks' `implements` links. Drafts stay free, so only what
  the user cares about is locked.
- *Requirements form a graph with versioned links.* A child records the parent version it was
  reviewed against; a newer parent version makes the child and its subtree suspect, so after a
  change the requirements and the done tasks to re-verify are known without guessing. A reviewed
  child that keeps its text clears its own subtree, so a change spreads only as far as it matters.
  Requirements rewritten in the same ECR are relinked to each other's new versions (otherwise they
  stay suspect and have to be reviewed with the ECR's own approval).

**Integrity**
- *Every command is a transaction* (`pm/txn.py`): an exclusive lock, a snapshot, the command, then
  the invariants; any failure restores the snapshot. The invariants (`invariants()` in pm.py)
  are the semantic rules in one place; *follow-ups* (`followups()`) are expected consequences of
  an approved change that later commands resolve, so they are warned about but not refused.
- *Limits:* the checks detect inconsistent states and changed locked texts, not every possible hand
  edit. A hand edit that leaves a consistent state (e.g. deleting the newest task and lowering
  its counter) is visible only in git history. The scripts protect against mistakes, not against
  deliberate tampering.

**Tasks**
- *Two-level grouping* (area N, topic N.M) defined in one JSON file: names are validated, so a
  typo cannot create a new group silently; order numbers give a stable reading order, and
  `group rename` keeps the tasks consistent.
- *One directory per task, state = directory.* State changes are atomic moves, git history
  follows the task, and agents never fight over one big file. (An alternative used elsewhere,
  four Markdown files with one list item per task, works for small projects but needs care to
  keep a task in exactly one file.)
- *Generated overviews plus `check` before every commit.* Hand-written statuses and overviews always
  drifted; hand edits to generated files were lost. With `check` in a pre-commit hook or CI neither can
  happen unnoticed.
- *Derived status.* `ready` appears by itself when the last dependency is done; `Needed by`
  shows what a slipping task delays. Open questions give `waiting`, so a task that waits for the
  user never looks startable.
- *A separate `dropped` state.* A rejected task kept in `done/` would wrongly satisfy the
  dependencies of other tasks; deleting it loses the history.
- *IDs only from the tool, the counter raised before the directory is created.* Hand-picked IDs
  collided across sessions; an interrupted run now skips an ID instead of reusing one. Start
  with four digits: one project had to migrate from three.
- *`context` on each task.* A new session or a subagent understands why a task exists without
  reading the history.
- *Append-only dated entries in `task.md`, with Result and Not done.* Rewritten status text lost
  history; "Not done" makes scope cuts visible; "Result" with commands and numbers answers
  "was this tested?" months later.

**Questions and decisions**
- *Question IDs only from the tool, one JSON file per question.* Hand numbering produced duplicates; "repeat Q-12" with a
  new number confused the user. Short answers like "Q-12: a, Q-13: b" are unambiguous. The
  answer is checked against the option letters.
- *Self-contained questions with a recommendation.* Questions that relied on earlier chat were
  unreadable in a question dialog; a concrete recommendation makes approvals quick.
- *Decisions verbatim and dated; proposals marked as proposals.* Later sessions treated an
  agent's proposal as a user decision, or re-litigated decisions that lived only in chat.
- *Open questions repeated at the end of every report.* Among many interleaved requests,
  pending decisions were otherwise forgotten.

**Way of working**
- *Verify the negative case; report what was not verified.* Caught permissions broader than
  intended, and keeps reports honest.
- *`date` before every time stamp.* Guessed times came out wrong, even in the future.
- *Commit only with the user's permission.* Several sessions committed too early before this rule.
- *Subagents: inbox file, foreground jobs, no self-matching `pgrep -f`.* Background jobs in
  subagents and self-matching wait loops hung or killed the agent's own shell.
- *Peer requests are not approvals.* A request from another agent session cannot grant what
  this session's user has not approved.

## Variants considered and not taken

- Questions as one directory each with open/closed states: one JSON file per question was
  kept, but open/closed is derived from the answers instead of a directory.
- Questions only inside the blocking task, no IDs. Works with few questions; breaks down when
  several are open at once.
- Plain `STATUS.md` + `LOG.md` without tasks, for operations work driven by requests. Its
  strengths live on here as `JOURNAL.md` and the reporting rules.
